# 하이브리드 검색 최적화: 제안 방법 vs 표준 기법 비교 및 선택 근거

## 왜 표준 기법과 다른 제안을 했는가?

### 1. 초기 제안의 배경

제가 처음 제안한 방법들은 **"빠른 구현 + 최소 의존성"**을 목표로 했습니다:

#### 제안한 방법의 특징
- ✅ **추가 라이브러리 없음**: 순수 Python + 정규표현식
- ✅ **빠른 구현**: 1-2일 내 완성 가능
- ✅ **의존성 최소화**: 기존 `requirements.txt` 변경 없음
- ✅ **성능 오버헤드 적음**: 라이브러리 초기화 시간 없음
- ⚠️ **정확도 제한**: 하드코딩된 규칙의 한계

#### 표준 기법의 특징
- ✅ **높은 정확도**: 검증된 라이브러리 사용
- ✅ **범용성**: 다양한 케이스 처리 가능
- ⚠️ **추가 의존성**: KoNLPy, spaCy, rapidfuzz 등
- ⚠️ **설치 복잡도**: 특히 KoNLPy는 Java 의존성 필요
- ⚠️ **성능 오버헤드**: 라이브러리 초기화 시간

### 2. 현재 프로젝트 상황 분석

#### 현재 의존성 (`requirements.txt`)
```
- rank-bm25>=0.2.2  (BM25 검색)
- sentence-transformers>=2.2.0  (Reranker)
- langchain 관련
- 기본 문서 처리 라이브러리들
```

**추가 라이브러리 없음** - 최소한의 의존성 유지

#### 프로젝트 특성
- **사내망 환경**: 외부 라이브러리 설치 제약 가능
- **로컬 실행**: Ollama 기반 오프라인 환경
- **빠른 배포**: 복잡한 설정 없이 동작해야 함

### 3. 제안 방법의 장단점

#### 장점
1. **즉시 적용 가능**
   - 코드 수정만으로 구현
   - 테스트 및 배포 빠름

2. **의존성 관리 용이**
   - 새로운 라이브러리 버전 충돌 없음
   - 설치 문제 없음

3. **성능**
   - 라이브러리 초기화 시간 없음
   - 메모리 사용량 적음

4. **유지보수**
   - 코드가 단순하고 이해하기 쉬움
   - 디버깅 용이

#### 단점
1. **정확도 제한**
   - 하드코딩된 규칙의 한계
   - 예외 케이스 처리 어려움

2. **확장성**
   - 새로운 패턴 추가 시 코드 수정 필요
   - 도메인 특화 어려움

3. **범용성**
   - 저자 이름에 특화
   - 다른 고유명사 처리 제한적

### 4. 표준 기법의 장단점

#### 장점
1. **높은 정확도**
   - 검증된 알고리즘
   - 다양한 케이스 처리

2. **범용성**
   - 저자 이름뿐만 아니라 모든 고유명사
   - 다양한 언어 지원

3. **확장성**
   - 새로운 패턴 자동 학습 가능
   - 도메인 특화 용이

#### 단점
1. **설치 복잡도**
   - KoNLPy: Java 설치 필요
   - spaCy: 모델 다운로드 필요
   - rapidfuzz: 추가 의존성

2. **성능 오버헤드**
   - 라이브러리 초기화 시간
   - 메모리 사용량 증가

3. **유지보수**
   - 라이브러리 버전 관리
   - 업데이트 시 호환성 확인 필요

### 5. 선택 기준 및 권장 사항

#### 상황별 권장 방법

##### 시나리오 1: 빠른 개선이 필요한 경우
**→ 제안한 방법 (하드코딩 규칙)**
- 1-2일 내 구현 가능
- 즉시 효과 확인
- 나중에 표준 기법으로 업그레이드 가능

##### 시나리오 2: 장기적 정확도가 중요한 경우
**→ 표준 기법 (라이브러리 사용)**
- 높은 정확도 필요
- 다양한 케이스 처리 필요
- 설치 환경 제약 없음

##### 시나리오 3: 하이브리드 접근 (권장)
**→ 단계적 적용**
1. **Phase 1**: 제안한 방법으로 빠른 개선
2. **Phase 2**: 표준 기법으로 점진적 업그레이드
3. **Phase 3**: 성능 비교 후 최적 방법 선택

### 7. 최종 권장 사항

#### 즉시 적용 (Phase 1)
1. **대소문자 정규화** (제안 방법)
   - 간단하고 효과적
   - 의존성 없음

2. **기본 변형어 생성** (제안 방법)
   - 2단어 패턴 처리
   - 빠른 구현

#### 선택적 적용 (Phase 2)
3. **Fuzzy Matching** (표준 기법)
   - `rapidfuzz` 라이브러리 (가벼움)
   - 오타 처리 효과적

4. **동의어 사전** (하이브리드)
   - 파일 기반 사전 구축
   - LLM 호출 없이 빠른 처리

#### 장기 적용 (Phase 3)
5. **NER** (표준 기법)
   - spaCy 또는 KoNLPy
   - 모든 고유명사 처리

6. **형태소 분석기** (표준 기법)
   - KoNLPy (선택적)
   - 성능 테스트 후 결정

### 8. 결론

**제안한 방법이 표준 기법과 다른 이유:**

1. **프로젝트 특성 고려**
   - 최소 의존성 유지
   - 빠른 배포 필요
   - 사내망 환경 제약

2. **단계적 접근**
   - 빠른 개선 → 점진적 업그레이드
   - 효과 확인 후 투자 결정

3. **실용성 우선**
   - 80% 효과를 20% 노력으로
   - 나머지 20%는 필요 시 추가

**최종 권장:**
- **즉시**: 제안한 방법으로 빠른 개선
- **단기**: Fuzzy Matching 추가 (rapidfuzz는 가벼움)
- **장기**: 성능 비교 후 NER/형태소 분석기 도입 여부 결정
