# RAG 시스템 전체 파이프라인 아키텍처

## 📖 시스템 개요

본 RAG (Retrieval-Augmented Generation) 시스템은 **2개의 독립적인 파이프라인**으로 구성됩니다:

### Pipeline A: 문서 인제스션 (Document Ingestion)
> 📥 **문서 업로드 → 청킹 → 비전 처리 → 임베딩 → 저장**
>
> PDF, PPTX, DOCX 등의 문서를 처리하여 검색 가능한 벡터 데이터베이스를 구축합니다.
> **비전 LLM**을 활용하여 표, 차트, 이미지를 자연어 설명으로 변환합니다.

### Pipeline B: 질의 응답 (Question Answering)
> 💬 **사용자 질문 → 검색 → 재순위 → 답변 생성 → Citation**
>
> 저장된 문서에서 관련 정보를 검색하고, LLM을 통해 답변을 생성합니다.
> Hybrid Search, Reranking, Multi-Query 등 고급 기법을 활용합니다.

### 비전 처리 세부 사항

#### Hybrid 모드 (기본 설정)
현재 시스템은 **Hybrid Vision Mode**를 사용합니다:

1. **텍스트가 충분한 페이지**: OCR 또는 텍스트 추출만 수행 (Vision LLM 스킵)
2. **표/차트/이미지가 있는 페이지**: Vision LLM 호출
3. **판단 기준**: 텍스트 양, 이미지 영역 비율

**장점**:
- 비용 절감 (불필요한 Vision API 호출 제거)
- 처리 속도 향상
- 정확도 유지 (시각 자료만 Vision 처리)

#### Vision API 설정 옵션

| 설정 항목 | 설명 | 기본값 |
|----------|------|--------|
| `vision_api_type` | API 타입 (openai, ollama, openai-compatible) | openai |
| `vision_model` | 모델명 | gpt-4o-mini |
| `vision_base_url` | API 엔드포인트 | https://api.openai.com/v1 |
| `pdf_vision_detail` | 이미지 해상도 (high, low, auto) | high |
| `pdf_dpi` | PDF → 이미지 변환 DPI | 150 |
| `enable_vision_chunking` | Vision 청킹 활성화 여부 | true |

### 파이프라인 A 메트릭

| 지표 | 범위 | 설명 |
|------|------|------|
| **처리 속도 (Vision OFF)** | 10-30초/파일 | 텍스트 청킹만 |
| **처리 속도 (Vision ON)** | 30-120초/파일 | Vision LLM 포함 (페이지 수에 비례) |
| **Vision API 비용** | $0.001-0.01/페이지 | GPT-4o-mini 기준 |
| **청크 수** | 5-50개/파일 | 파일 크기 및 복잡도에 따라 |
| **임베딩 차원** | 1024차원 | mxbai-embed-large 기준 |

## ⚖️ 각 단계별 장단점 및 대안

### Pipeline A 단계

#### 1. Vision Processing
- **장점**: 표/차트/이미지의 정확한 의미 추출, 시각 자료 검색 가능
- **단점**: Vision API 비용, 처리 시간 증가, 정확도 한계
- **대안**: OCR만 사용 (저비용), Hybrid 모드 (균형), Table Detection 전용 모델

#### 2. Embedding Vectorization
- **장점**: 의미 기반 검색 가능, 다국어 지원, 임베딩 모델 교체 용이
- **단점**: 벡터 저장 공간, 임베딩 생성 시간
- **대안**: TF-IDF (전통적), Sparse 임베딩 (SPLADE)

### Pipeline B 단계

#### 1. File Mention Detection
- **장점**: 즉각적인 파일 특정, LLM 비용 없음, 사용자 의도 명확
- **단점**: @기호 필수 사용, 자연어 인식 불가
- **대안**: NER(Named Entity Recognition), LLM 기반 파일명 추출

#### 2. Intent Detection + Session Context
- **장점**: "이 문서", "방금 올린 파일" 자연어 인식, 사용자 편의성
- **단점**: 5분 타임아웃 제약, 여러 문서 업로드 시 모호성
- **대안**: 대화 이력 전체 분석, 영구 문서 추적

#### 3. Question Classification
- **장점**: 질문별 최적 파라미터 자동 조정, 검색 효율 최대화
- **단점**: LLM 모드 지연, 오분류 시 성능 저하
- **대안**: 강화학습 기반 파라미터 선택, A/B 테스트 기반 최적화

#### 4. Multi-Query Rewriting
- **장점**: 재현율 대폭 향상, 다양한 표현 커버
- **단점**: LLM 비용/지연, 불필요한 쿼리 생성 가능
- **대안**: Embedding space에서 유사 쿼리 생성, GPT Cache 사용

#### 5. Hybrid Retrieval (BM25 + Vector)
- **장점**: 키워드+의미 검색 강점 결합, 전문용어 검색 강화
- **단점**: BM25 인덱스 메모리, 계산 비용 증가
- **대안**: Sparse-Dense 통합 모델 (SPLADE, ColBERT)

#### 6. Reranking
- **장점**: 정밀도 대폭 향상, Top-K 품질 보장
- **단점**: Cross-Encoder 계산 비용 높음 (1-3초)
- **대안**: Bi-Encoder만 사용 (빠름), Cohere Rerank API (클라우드)

#### 7. Score Filtering
- **장점**: 노이즈 문서 자동 제거, 질문별 동적 조정
- **단점**: 파라미터 튜닝 필요, 최소 문서 수 미달 가능성
- **대안**: MMR (Diversity), LLM 기반 relevance 판단

#### 8. Answer Verification
- **장점**: 상용 서비스 수준 품질 보증, 환각 방지
- **단점**: 추가 LLM 호출, 과도한 제약은 창의성 저해
- **대안**: 사용자 피드백 루프, RL from Human Feedback

#### 9. Self-Consistency
- **장점**: 환각 감소, 불확실성 측정 가능
- **단점**: 비용 3배, 지연 3배
- **대안**: Beam Search, Chain-of-Thought, Temperature=0

#### 10. Citation Insertion
- **장점**: 출처 추적 가능, 신뢰도 향상
- **단점**: 정확한 매칭 어려움, 가독성 저하
- **대안**: LLM이 직접 citation 생성 (더 자연스러움)

## 📈 성능 최적화 포인트

### 속도 개선 가능 영역
1. **Vision Hybrid Mode 활성화**: 텍스트 페이지는 Vision 스킵 (30-50% 속도 향상)
2. **Multi-Query 비활성화** (특정 질문 유형): 0.5-2초 절약
3. **Reranker 제거** (간단한 질문): 1-3초 절약
4. **Self-Consistency 비활성화**: 비용/시간 3배 절약
5. **Embedding Cache**: 동일 쿼리 재검색 시 즉시 반환

### 정확도 개선 가능 영역
1. **Vision Model 업그레이드**: GPT-4o-mini → GPT-4o (더 정확한 표/차트 해석)
2. **Reranker 모델 업그레이드**: bge-reranker-large 사용
3. **Question Classifier LLM 모드 활성화**: 분류 정확도 향상
4. **Score Threshold 조정**: 질문 유형별 최적값 실험
5. **Prompt Engineering**: 질문 타입별 프롬프트 세밀 조정

### 비용 절감 가능 영역
1. **Vision Hybrid Mode**: 불필요한 Vision API 호출 제거 (50-70% 비용 절감)
2. **Multi-Query 수 감소**: 3개 → 2개
3. **Self-Consistency 비활성화**: 비용 3배 절약
4. **Question Classifier 휴리스틱 모드**: LLM 호출 제거
5. **Reranker initial_k 감소**: 100 → 40

## 🎯 개선 제안

### 단기 개선 (Low-hanging fruits)
1. **Embedding Cache 구현**: 동일 쿼리 재사용
2. **Reranker Batch Processing**: 여러 쿼리 동시 rerank
3. **Async Retrieval**: Multi-Query 병렬 처리
4. **Prompt Caching**: 반복 프롬프트 캐싱
5. **Vision API Cache**: 동일 이미지 재처리 방지

### 중기 개선
1. **Fine-tuned Reranker**: 도메인 특화 reranker 학습
2. **Query Understanding Module**: 복잡한 질문 분해
3. **Result Diversification**: MMR, Clustering
4. **User Feedback Loop**: 사용자 평가 기반 개선
5. **Table Detection Model**: 표 전용 검출 모델 통합

### 장기 개선
1. **End-to-End 학습**: Retrieval + Generation 통합 학습
2. **Graph RAG**: 문서 간 관계 그래프 활용
3. **Multi-Modal Embedding**: 이미지를 직접 벡터화 (CLIP, BLIP-2)
4. **Agentic RAG**: LLM이 검색 전략 스스로 결정
5. **Continual Learning**: 사용자 피드백 기반 모델 업데이트

## 📊 파이프라인 메트릭

### Pipeline A 메트릭
- **문서 처리 시간**: 10-120초/파일 (Vision 사용 여부에 따라)
- **Vision API 호출 수**: 0-N회 (페이지 수, Hybrid Mode)
- **임베딩 생성 시간**: 0.1-0.5초/청크
- **저장 용량**: ~1MB/파일 (벡터 포함)

### Pipeline B 메트릭
- **검색 시간**: context retrieval (0.5-3초)
- **생성 시간**: LLM first token delay (0.2-1초)
- **전체 응답 시간**: query_stream total (1-5초)
- **검색된 문서 수**: 3-20개 (동적 조정)
- **신뢰도 점수**: 0-100 (평균 70-90)
- **재생성 비율**: 답변 검증 실패 → 재생성 (5-10%)

### 품질 지표
- **정밀도 (Precision)**: 검색된 문서 중 관련 문서 비율
- **재현율 (Recall)**: 관련 문서 중 검색된 문서 비율
- **MRR (Mean Reciprocal Rank)**: 첫 관련 문서 순위
- **NDCG**: 순위 품질 종합 지표
- **사용자 만족도**: 답변 유용성 평가
